Introduction

NIMBLE code is written in a slightly unusual format if you’re used to just using base R. It is written in the style of a program called BUGS, which came out a few decades ago and was developed at Imperial College London. But you don’t really need to know about BUGS to be able to use NIMBLE.

We will start with some straightforward examples for situations you’re likely familiar with to introduce the style of writing models. These examples will feature basic regression models using linear predictors.

Some of these models have been adapted from NIMBLE’s examples.

Normal-Normal example

\[ \begin{split} y_i &\sim \text{Normal}(\mu_i, \sigma) \quad i = 1,..., N \\ \mu_i &= \alpha + \beta_1 x_1 + \beta_2 x_2 + \beta_3 x_3 \\ \alpha &= 0 \\ \beta_1 &= 0.2 \\ \beta_2 &= 0.5 \\ \beta_3 &= 0.3 \\ \sigma &= 0.5\\ \end{split} \]

First create some example data:

set.seed(1)

p <- 3 # number of explanatory variables
n <- 10000 # number of observations
X <- matrix(round(rnorm(p * n), 2), nrow = n, ncol = p) # explanatory variables
true_betas <- c(0.2, 0.5, 0.3) # coefficients for beta1, beta2, beta3
sigma <- 0.5 # standard deviation of variability around perfect agreement
y <- rnorm(n, X %*% true_betas, sigma)

We also centre the three explanatory variables now, which helps MCMC performance later. Centring shifts the intercept but leaves the slopes unchanged, so the frequentist and Bayesian fits below are directly comparable.

x1 <- X[, 1] - mean(X[, 1])
x2 <- X[, 2] - mean(X[, 2])
x3 <- X[, 3] - mean(X[, 3])

Let’s rewrite this model in a Bayesian framework using NIMBLE. It can be written in lots of different ways, but here we’re going to try and stick to defining the priors first, then writing the formula.

code <- nimbleCode({
  # priors for parameters
  alpha ~ dnorm(0, sd = 100) # prior for alpha
  beta1 ~ dnorm(0, sd = 100) # prior for beta1
  beta2 ~ dnorm(0, sd = 100) # prior for beta2
  beta3 ~ dnorm(0, sd = 100) # prior for beta3
  sigma ~ dunif(0, 100) # prior for variance components

  # regression formula
  for (i in 1:n) {
    # n is the number of observations we have in the data
    mu[i] <- alpha + beta1 * x1[i] + beta2 * x2[i] + beta3 * x3[i] # manual entry of linear predictors
    y[i] ~ dnorm(mu[i], sd = sigma)
  }
})

First a summary of how the statistics of the samples of each parameter look

5 sigma     0.504    0.500   0.0747  0.00348  0.492  0.520

Every column here is a summary of the samples themselves, so it is worth being clear about what each one is telling us:

  • mean is the average of all the retained samples for that parameter, and is the usual point estimate of the posterior.
  • median is the 50th percentile of the samples. Comparing it against mean is a quick check on skewness: if the two are close, the posterior is roughly symmetric.
  • sd is the standard deviation of the samples, describing how wide the posterior is. Note this is a description of the posterior itself rather than a standard error in the frequentist sense, even though the two often end up numerically similar.
  • mad is the median absolute deviation, calculated as 1.4826 * median(abs(x - median(x))). The constant rescales it so that for a Normal distribution it estimates the same quantity as sd. Because it is built out of medians rather than squared distances, it is not dragged around by a handful of extreme samples.
  • q5 and q95 are the 5th and 95th percentiles of the samples, which together give a 90% credible interval. Unlike the frequentist confidence interval above, this is a direct probability statement about the parameter.

For alpha and the three betas the two columns agree almost exactly, which tells us those posteriors are well behaved. For sigma they disagree by a factor of about twenty (roughly 0.075 against roughly 0.003). That gap is important: a few extreme samples are inflating sd while leaving the robust measure alone. We will see below where those samples came from.

Then examine how well the model has converged, which typically is identified by how close each rhat value is to 1.00. As in the lecture, rhat compares variation within each chain to variation between the four chains, which is why running more than one chain matters here. If it is much above 1.00 (>1.05) then the samples will not be very well converged and therefore either the model is not well specified or there just needs to be more iterations of the MCMC. It is a little bit of an art to figure that out, but rhat helps.

summarise_draws(nimbleMCMC_samples_initial, default_convergence_measures())
# A tibble: 5 × 4
  variable  rhat ess_bulk ess_tail
  <chr>    <dbl>    <dbl>    <dbl>
1 alpha    1.00    7626.    7612. 
2 beta1    1.00    7625.    7373. 
3 beta2    1.000   8013.    6992. 
4 beta3    1.00    7998.    7287. 
5 sigma    1.06      44.9     26.9

The three columns here are each doing a different job:

  • rhat compares the variation within each chain against the variation between the four chains, as described above. It is a ratio of two variance estimates, so when the chains have mixed well it will sometimes come out fractionally below 1.00. Only the upper tail carries information, so 0.999 and 1.000 tell us the same thing.
  • ess_bulk is the effective sample size in the bulk of the posterior, calculated on rank-normalised samples. It is the number that governs how much we can trust mean and median. Because MCMC samples are correlated with one another, one sample is usually worth less than one independent draw, so this is typically smaller than the number of samples we actually collected.
  • ess_tail is the smaller of the effective sample sizes at the 5% and 95% quantiles, and governs how much we can trust q5 and q95.

We need both effective sample sizes because a chain can move around the middle of a posterior perfectly well while exploring the extremes poorly. That would give us a trustworthy mean alongside untrustworthy credible interval endpoints, and looking at ess_bulk alone would hide it. A rough working rule is that we want at least 100 effective samples per chain for these summaries to mean anything, so at least 400 here with our four chains.

You may also occasionally see an effective sample size slightly larger than the number of samples collected. This is not an error. The effective sample size is estimated from the autocorrelation of the chain, and that estimate is itself a little noisy, so a small excess is nothing to read into.

Looking at the table, alpha and the three betas are in excellent shape on all three columns. sigma is not: its rhat is above the 1.05 threshold and its effective sample sizes are in the tens rather than the thousands. This is the same problem the sd and mad disagreement was pointing at.

Let’s focus on the sigma plot

mcmc_trace(nimbleMCMC_samples_burnin, pars = c("sigma"))

This trace looks different from the beta traces. Where the beta chains cross their mean on almost every iteration, sigma wanders: it drifts up for a stretch of samples, then drifts back down. That wandering is what the lower effective sample size in the table above is measuring, because a run of samples that all sit on the same side of the mean carries less information than the same number of independent draws would.

The reason has nothing to do with the burn in, and not much to do with the model being difficult. It is about which sampler NIMBLE assigned to each parameter. We can look directly at the configuration we built earlier.

mcmcConf$printSamplers()
[1] conjugate_dnorm_dnorm_additive sampler: alpha
[2] conjugate_dnorm_dnorm_linear sampler: beta1
[3] conjugate_dnorm_dnorm_linear sampler: beta2
[4] conjugate_dnorm_dnorm_linear sampler: beta3
[5] RW sampler: sigma

alpha and the three betas have been given conjugate samplers, because a Normal prior combined with a Normal likelihood is one of the conjugate relationships NIMBLE detects automatically. A conjugate sampler draws directly from the full conditional distribution, so consecutive samples are essentially independent of one another. That is why their effective sample sizes come out at roughly the number of samples we collected.

sigma has been given an adaptive random walk Metropolis sampler instead. Our prior for it was dunif(0, 100), which is not conjugate to the Normal likelihood, so NIMBLE falls back on a general purpose sampler. A random walk proposes a small step away from wherever the chain currently sits, then accepts or rejects it. Consecutive samples are correlated by construction, and that is exactly the drifting we can see in the trace.

It is worth saying clearly that this is not a broken sampler. Roughly 880 effective samples out of 4000 is about what a well tuned adaptive random walk achieves for a single parameter, and both rhat and the effective sample sizes are comfortably past the thresholds set out above. The model is fine. But it is a useful illustration that effective sample size tells us about the sampler at least as much as it tells us about the model.

If we do want sigma to mix as well as the betas do, the cleanest route is to give it a conjugate prior too. For a Normal likelihood the conjugate prior for the variance is the inverse gamma, so we put the prior on the variance and then take a square root to recover the standard deviation.

code_conjugate_sigma <- nimbleCode({
  # priors for parameters
  alpha ~ dnorm(0, sd = 100) # prior for alpha
  beta1 ~ dnorm(0, sd = 100) # prior for beta1
  beta2 ~ dnorm(0, sd = 100) # prior for beta2
  beta3 ~ dnorm(0, sd = 100) # prior for beta3
  sigma2 ~ dinvgamma(shape = 0.01, scale = 0.01) # prior on the variance this time
  sigma <- sqrt(sigma2) # recover the standard deviation for comparability

  # regression formula
  for (i in 1:n) {
    mu[i] <- alpha + beta1 * x1[i] + beta2 * x2[i] + beta3 * x3[i]
    y[i] ~ dnorm(mu[i], var = sigma2) # note the var parameterisation
  }
})

Note that the likelihood is written with var = sigma2 rather than sd = sigma. This matters. NIMBLE detects conjugacy by inspecting how nodes are connected in the model graph, and routing the variance through a deterministic square root before it reaches the likelihood would hide the relationship.

Initial values again, this time squared versions of the ones we used before so the chains start in equivalent places.

Two caveats are worth attaching to this. First, we changed the prior in order to get here, and choosing a prior for computational convenience rather than because it represents what we actually believe is a habit to be wary of. It does no damage in this particular case because we have many observations and the data overwhelm the prior, which you can check by comparing the estimates against the earlier run. It is a much bigger problem for variance parameters in hierarchical models, where an inverse gamma prior behaves poorly if the variance can be close to zero.

Second, changing the prior is not the only option available. If we wanted to keep dunif(0, 100), we could instead leave the model alone and swap the sampler using mcmcConf$removeSamplers() and mcmcConf$addSampler(), choosing a slice sampler or a random walk on the log scale. Or we could simply run more iterations, since effective sample size grows roughly in proportion to the number of samples collected.

Let’s try changing the priors and see if that makes any difference to how the model fits. Take some time to compare this with the code for the original model above. Notice how the real value of beta2 (0.5) is not allowed as a value from the prior it is assigned below.

Back to our sensible priors, say we wanted to establish the estimated difference between two betas? Let’s say beta1 and beta2 in this case. NIMBLE formulas are flexible so you can define this as an output of the model, as seen in last elements of formula code below.

code_diff_betas <- nimbleCode({
  # priors for parameters
  alpha ~ dnorm(0, sd = 100) # prior for alpha
  beta1 ~ dnorm(0, sd = 100) # prior for beta1
  beta2 ~ dnorm(0, sd = 100) # prior for beta2
  beta3 ~ dnorm(0, sd = 100) # prior for beta3
  sigma ~ dunif(0, 100) # prior for variance components

  # regression formula
  for (i in 1:n) {
    mu[i] <- alpha + beta1 * x1[i] + beta2 * x2[i] + beta3 * x3[i]
    y[i] ~ dnorm(mu[i], sd = sigma)
  }

  # difference between beta1 and beta2
  beta12_diff <- beta2 - beta1

Logistic regression (binomial) example

Logistic regression is used when we want to classify observations into two groups. \[ \begin{split} y_i &\sim \text{Bernoulli}(p_i) \quad i = 1,..., N \\ \text{logit}(p_i) &= \alpha + \beta_1 x_1 + \beta_2 x_2 + \beta_3 x_3 \end{split} \]

Note, a Bernoulli likelihood is equivalent to a Binomial with sample size 1.

First create some example data for our model (for success (1) or failure (0) as the outcome):

n <- 10000
p <- 3

set.seed(1)
x1 <- round(rnorm(n), 2)
x2 <- round(rnorm(n), 2)
x3 <- round(rnorm(n), 2)

z <- 1 + 2 * x1 + 3 * x2 - 5 * x3 # linear combination with a bias of 1
pr <- 1 / (1 + exp(-z)) # pass through an inv-logit function
y <- rbinom(n, 1, pr) # bernoulli response variable

# centre the explanatory variables, as in the Normal example above
x1 <- x1 - mean(x1)
x2 <- x2 - mean(x2)
x3 <- x3 - mean(x3)

Create the NIMBLE model for a logistic regression.

code_binomial <- nimbleCode({
  # priors for parameters
  alpha ~ dnorm(0, sd = 100) # prior for alpha
  beta1 ~ dnorm(0, sd = 100) # prior for beta1
  beta2 ~ dnorm(0, sd = 100) # prior for beta2
  beta3 ~ dnorm(0, sd = 100) # prior for beta3

  # regression formula
  for (i in 1:n) {
    y[i] ~ dbin(p[i], 1)
    logit(p[i]) <- alpha + beta1 * x1[i] + beta2 * x2[i] + beta3 * x3[i]
  }
})

Closing remarks

In this lab session, we have explored how to fit some basic models using Bayesian regression in NIMBLE. We looked at the three most common likelihoods: Normal, Binomial, and Poisson.

Throughout we ran four chains from different starting values, which is what makes rhat a meaningful convergence check, and we also looked at the effective sample size of each parameter to make sure we have enough samples to make inferences about the posterior distributions. We will keep doing both later in the workshop when we look at more complex models.

We used simulated data here, so we had complete control over the complexity in the data. However, in the real world, we would often try many different models if we do not know how the data were generated. Also, not all real life examples fit any of the three likelihoods perfectly. For example, the data might be “overdispersed”, where there is greater variability in the data than would be expected. Luckily, there are extensions to these likelihoods that can deal with overdispersion, such as the beta-binomial likelihood for overdispersed binomial data, or the negative binomial likelihood (sometimes called the gamma-Poisson) for overdispersed Poisson data. For more information on these likelihoods, see Chapter 12 of Statistical Rethinking by Richard McElreath.
